# Host Connector

Status: Accepted target specification. The current `JulOS.Agent` implementation is the migration source. New work uses **Host Connector** exclusively. Historical work-item IDs, release notes and audit events keep their original names.

## 1. Purpose

The JulOS Host Connector is a small process installed on a host whose local resources JulOS must reach. It establishes an outbound authenticated connection to JulOS Server and exposes only explicitly enabled, versioned capabilities.

The Host Connector is infrastructure, not a desktop application. It is not:

- an AI agent;
- Hermes or another assistant;
- a chat surface;
- a generic remote shell;
- a Docker API proxy;
- a package worker;
- Runtime Manager.

The product UI calls this area **Host access**. The technical term in code, contracts and diagnostics is **Host Connector**.

## 2. Ownership boundaries

Host Connector owns:

- enrollment and durable host identity;
- outbound transport, reconnect and protocol negotiation;
- local collection of explicitly enabled host observations;
- validation and execution of typed host-adapter requests;
- target-side enforcement of roots, engine scopes, deadlines and output limits;
- bounded byte streams requested by a typed capability.

Host Connector does not own:

- Docker application interpretation, catalog metadata or user-facing Docker policy;
- Proxmox, Files, Discovery or Remote business logic;
- arbitrary command strings;
- application windows or sessions;
- JulOS-owned helper/session containers.

The owning package validates domain intent before requesting a host capability. The Host Connector independently validates the target-side scope. Both checks are mandatory.

## 3. Process and deployment model

One Host Connector process serves one enrolled host. A target host that JulOS only reaches through an external public API does not require a Connector. A host whose Docker engine, local files, local network or metrics JulOS manages does require one.

Supported initial deployment forms:

- a system service using the published Host Connector binary;
- a container with only the host resources needed by its enabled capabilities;
- a Compose service installed beside JulOS on the local Docker host.

A containerized Connector may receive the Docker socket only on the target host and only when Docker capabilities are enabled. JulOS Server and Runtime Manager never receive that socket. A Connector without Docker capability receives no Docker socket.

## 4. Identity and enrollment

Persistent identity:

```text
HostConnectorId
MachineIdentity
DisplayName
OperatingSystem
Architecture
Version
ProtocolVersion
State
EnrolledAtUtc
LastSeenAtUtc
RevokedAtUtc
Revision
```

Rules:

- `HostConnectorId` is generated by Server and remains stable across process and container recreation.
- `MachineIdentity` is a privacy-bounded hash used to detect accidental duplicate enrollment; it is not a display name.
- enrollment uses a short-lived, single-use token;
- the Connector generates and protects its durable credential locally;
- revocation is terminal for that credential;
- re-enrollment creates a new credential only after an administrator deliberately starts a new enrollment;
- ephemeral IP addresses, hostnames and container IDs are not persistent identity.

The target identity file is `/var/lib/julos-host-connector/identity.json` on Linux unless explicitly configured. It must be a regular file, must not be a symbolic link and must be readable only by the Connector identity.

Protocol-v1 credential contract:

```text
CredentialV1 = Base64urlWithoutPadding(RandomBytes(48))
ServerValue  = SHA256(decoded CredentialV1 bytes)
```

Enrollment request contains token, credential, display name, Machine Identity, OS, architecture, version and protocol version. It is accepted only over HTTPS except loopback development. Server stores only `ServerValue` and returns Host Connector ID, accepted protocol and polling intervals; it never echoes the credential. An exact retry using the same token, credential hash and identity returns the original enrollment result; any changed token reuse fails. Runtime requests send `X-JulOS-Host-Connector-Id` plus `Authorization: Bearer <CredentialV1>`. Authentication uses constant-time hash comparison, and access/header logs redact Authorization.

Credential rotation is administrator-initiated through `POST /api/v1/host-connectors/{id}/credential-rotations` and uses a durable two-phase protocol. The protected local identity keeps its active `CredentialV1` plus an optional `PendingRotation { rotationId, pendingCredentialV1, phase, overlapExpiresAtUtc? }`; pending secret values never leave that file except in the TLS-protected attempt/acknowledgement requests.

1. Connector receives a one-use Rotation ID, generates a new CredentialV1 and atomically persists it as `phase=prepared` while the old credential remains active.
2. Authenticated with the old credential, it submits `{ newCredentialV1 }` to the attempt endpoint. Server stores only its hash, persists `overlap`, returns the exact expiry, and accepts old or pending authentication for at most ten minutes.
3. Connector persists `phase=overlap` and acknowledges authenticated with the pending credential. In one Server transaction, that hash becomes current, the old hash stops authenticating and the rotation becomes `committed`.
4. Only after a committed acknowledgement response does Connector promote the pending value to active and clear `PendingRotation` atomically.

Every step is exact-retry idempotent. A crash before Server commit leaves the old active value and recoverable pending value locally. Before any normal poll after restart, Connector first retries acknowledgement with the pending value; committed Server state returns the same success. If pending authentication is rejected, Connector retries the exact attempt with the still-stored old active value: an expired Server rotation returns `host_connector.credential_rotation_expired`, after which Connector clears the pending block and keeps the old value. Rejection of both credentials is a visible hard failure and never triggers enrollment. It never owns only an unaccepted credential and never leaves two hashes valid indefinitely.

## 5. Protocol

The target runtime prefix is:

```text
/api/v1/host-connector
```

Every runtime request carries:

```text
X-JulOS-Host-Connector-Protocol: 1
```

Server confirms:

```text
X-JulOS-Host-Connector-Protocol: 1
X-JulOS-Host-Connector-Protocol-Min: 1
X-JulOS-Host-Connector-Protocol-Max: 1
```

Missing or incompatible versions return HTTP `426` and `host_connector.protocol_incompatible`. Neither side silently downgrades.

Runtime endpoints are fixed:

```text
POST /api/v1/host-connector/enrollment
POST /api/v1/host-connector/heartbeat
POST /api/v1/host-connector/observations/host-metrics
GET  /api/v1/host-connector/requests/next?waitSeconds={1..30}
POST /api/v1/host-connector/requests/{requestId}/result
POST /api/v1/host-connector/credential-rotations/{rotationId}/attempt
POST /api/v1/host-connector/credential-rotations/{rotationId}/acknowledgement
```

The request poll is one bounded long-poll, returns `204` when empty and never becomes an arbitrary server-push channel. Disconnect retries use capped exponential backoff with jitter. Every registered operation declares `replay-safe` or `reconcile-required`. A replay-safe claim may be redelivered only with the same Request ID before deadline. A reconcile-required claim is never redelivered for execution: Connector journals its ID before the external call and its canonical result before submission. In-time restart from an uncertain `executing` phase submits `failed/host_connector.outcome_unknown` with a canonical digest; if no report arrives by deadline, Server records `expired/host_connector.outcome_unknown` without a result digest. Both require a new typed read-only inspection/reconciliation request and neither rewrites or replays the original mutation. `DATA_AND_API_CONTRACTS.md` owns the closed state-transition matrix.

Every dispatched request has:

```text
MessageId
ContractVersion
HostConnectorId
OperationId                 optional durable JulOS operation
CapabilityName
CapabilityVersion
OperationName
TargetReference
PayloadSchemaVersion
ResultSchemaVersion
Payload
RequestedAtUtc
DeadlineAtUtc
CorrelationId
MaximumResultBytes
IdempotencyClassification     replay-safe | reconcile-required
```

`MessageId` is exactly the persisted `HostConnectorRequestId` and the `{requestId}` path value used for result submission. The tuple `CapabilityName + CapabilityVersion + OperationName + PayloadSchemaVersion + ResultSchemaVersion` selects committed request and result schemas. Unknown tuples and unknown required fields are rejected before execution. `Payload` is not permission to accept arbitrary commands.

Result submission body:

```text
MessageId
ResultSchemaVersion
Outcome                     succeeded | failed | cancelled
Result                      nullable typed JSON
FailureCode                 nullable stable code
FailureDetail               nullable sanitized bounded text
```

The authenticated Connector ID, body Message ID and Result Schema Version must match the claimed request, URL and persisted result version exactly. `succeeded` requires a schema-valid Result and null failure fields; `failed`/`cancelled` require null Result and a registered failure code. Result bytes must fit `MaximumResultBytes`, contain no credential and canonicalize deterministically. Server stores the full canonical result-body digest before returning `200 { requestId, state, revision }`. An exact retry returns the same response; changed bytes after terminal completion return `409 host_connector.result_conflict`. Late success cannot revive an expired request. Binary or interactive data uses an authorized stream, never this JSON result.

### 5.1 Durable local request journal

Before executing a claimed request, Connector writes `/var/lib/julos-host-connector/request-journal/<requestId>.json` on Linux or `%ProgramData%\JulOS\HostConnector\request-journal\<requestId>.json` on Windows. `JULOS_HOST_CONNECTOR_JOURNAL_PATH` may replace the directory only with an absolute path; relative paths are rejected. The file schema is:

```text
JournalSchemaVersion             1
HostConnectorId
RequestId
ContractVersion
CapabilityName
CapabilityVersion
OperationName
PayloadSchemaVersion
ResultSchemaVersion
IdempotencyClassification       replay-safe | reconcile-required
RequestCanonicalJson
RequestDigest
DeadlineAtUtc
Phase                           prepared | executing | result-ready
ResultCanonicalJson             nullable
ResultDigest                    nullable
UpdatedAtUtc
```

The canonical request is the exact validated non-secret dispatch envelope; operation-bound Secret Leases and stream bytes are never journal fields. Request/Result digests are lowercase SHA-256 over RFC 8785 bytes. The journal directory is owner-only (`0700`) and each regular non-symlink file is `0600`; Windows uses an owner-only ACL. Each phase change writes a same-directory temporary file, flushes file contents, atomically replaces the target and flushes the directory (Windows: write-through atomic replace) before continuing.

Execution order is strict:

1. persist `prepared` before invoking any capability code;
2. persist `executing` before the first external side-effect call;
3. canonicalize the complete result and persist `result-ready` before HTTP submission;
4. delete and directory-flush only after Server returns the matching terminal `200` acknowledgement.

At startup Connector resolves journal files before polling new work. `prepared` before deadline may execute. `executing` may execute again only for `replay-safe`; for `reconcile-required`, Connector instead persists and submits a canonical failed result with `host_connector.outcome_unknown`. `result-ready` resubmits its exact bytes. A terminal rejection or passed deadline never causes execution: Connector creates a Problem and atomically replaces the journal with an owner-only `<requestId>.orphan.json` containing exactly `OrphanSchemaVersion=1`, Host Connector ID, Request ID, Request Digest, nullable Result Digest, terminal Failure Code, `OrphanedAtUtc` and `DeleteAfterUtc = OrphanedAtUtc + 7 days`. Canonical bodies are not retained; the orphan is deleted and directory-flushed at that instant. Malformed, duplicate-ID, symlink or permission-invalid journal files block request execution and create a Problem; they are never ignored or repaired silently.

## 6. Capabilities

Initial platform capabilities:

| Capability | Owner | Purpose |
|---|---|---|
| `host.metrics.linux/1` | Host Connector | Bounded Linux host observations |
| `host.connector.diagnostics/1` | Host Connector | Sanitized version, reconnect and capability snapshot |
| `host.stream/1` | Host Connector | Multiplexed stream bound to a typed parent request |
| `docker.inventory/1` | Host Connector adapter | Read JulOS-scoped Docker inventory |
| `docker.logs/1` | Host Connector adapter | Read bounded logs for a resolved service/container |
| `docker.control/1` | Host Connector adapter | Allowlisted lifecycle action on a resolved owned target |
| `docker.apps/1` | Host Connector adapter | Preflight/apply/inspect/remove/backup/restore an owned app installation |
| `docker.container.terminal/1` | Host Connector adapter | Attach a bounded exec stream to one resolved container |

Files and Discovery add their own capability contracts in their owning work items. A generic `host.command`, `shell.execute`, arbitrary TCP proxy or arbitrary Docker request is prohibited.

## 7. Host stream contract

`host.stream/1` is transport, not authority. A stream can open only after an authorized typed capability request creates a stream grant containing:

```text
StreamId
HostConnectorId
ParentOperationId
CapabilityName
UserId
TargetReference
Direction
MaximumBytesPerDirection
IdleTimeoutSeconds
ExpiresAtUtc
```

The Connector accepts only a grant authenticated by Server and matching the pending parent request. It cannot choose a different host, port, container or filesystem target. Stream close, timeout and byte-limit exhaustion are terminal and observable.

Web-application reachability, Remote display and container terminal reuse this transport only after their owning capability has authorized the concrete target.

## 8. Administration API

Browser-facing resources:

```text
POST /api/v1/host-connectors/enrollment-tokens
GET  /api/v1/host-connectors
GET  /api/v1/host-connectors/{hostConnectorId}
PUT  /api/v1/host-connectors/{hostConnectorId}
POST /api/v1/host-connectors/{hostConnectorId}/revocation
POST /api/v1/host-connectors/{hostConnectorId}/credential-rotations
POST /api/v1/host-connectors/{hostConnectorId}/diagnostics
GET  /api/v1/host-connectors/{hostConnectorId}/capabilities
```

All mutations require antiforgery protection. Rename uses optimistic concurrency. Diagnostics returns a durable Operation when target contact is required. The public API has no generic command-creation endpoint.

Credential-rotation creation requires `host_connectors.manage`, `Idempotency-Key` and `{ expectedRevision }`. It returns `202` with the durable Operation and Rotation ID; exact idempotency retry returns the same pair. A partial unique constraint rejects another `requested`/`overlap` rotation with `409 host_connector.credential_rotation_active`. An unattempted request expires after exactly fifteen minutes. Connector revocation atomically expires any active rotation and rejects both current and pending hashes.

Permissions:

```text
host_connectors.read
host_connectors.manage
host_connectors.diagnostics
```

Package-specific permissions, such as `docker.control`, remain separate.

Permission migration in HCON-002 is explicit:

- create all three Host Connector permissions before replacing endpoints;
- grant all three globally to the built-in Administrator role;
- copy each existing global `core.authorization.read` assignment to `host_connectors.read` for the same user/role;
- copy each existing global `core.authorization.manage` assignment to `host_connectors.read`, `host_connectors.manage` and `host_connectors.diagnostics`;
- do not widen package/resource-scoped assignments or infer rights from Connector enrollment;
- then switch read, rename/revoke/rotation and diagnostics endpoints to read, manage and diagnostics respectively.

Migration is idempotent and tested for unauthenticated `401`, authenticated missing-right `403`, read-only, diagnostics-only, manage and Administrator matrices.

## 9. Product UI

Host Connector is absent from the launcher and normal taskbar. `Settings → Hosts → Host access` shows:

- host name and state;
- last contact and version;
- enabled capabilities;
- enrollment instructions;
- diagnostics action;
- revoke action.

Package applications show target-host availability in their own context. A lost Connector creates a Problem and package-specific offline state; it does not create a permanent global launcher application.

## 10. Agent-to-Connector migration

The migration is one vertical work item and leaves no indefinite dual implementation.

### 10.1 Code and public names

- `JulOS.Agent` becomes `JulOS.HostConnector`.
- `JulOS.Domain.Agents` becomes `JulOS.Domain.HostConnectors`.
- contracts, endpoints, permissions, events, environment variables and tests use Host Connector names;
- `agent.status.changed` becomes `host_connector.status.changed` with a new contract version;
- historical release notes and historical audit actions are not rewritten.

### 10.2 Persistent schema

New migrations rename, without drop/recreate:

```text
agents                         → host_connectors
agent_capabilities             → host_connector_capabilities
agent_credentials              → host_connector_credentials (current hash)
new table                      → host_connector_credential_rotations
agent_enrollment_tokens        → host_connector_enrollment_tokens
agent_commands                 → legacy_agent_commands (read-only retention)
agent_metric_samples           → host_connector_metric_samples
agent_id                       → host_connector_id
redeemed_by_agent_id           → redeemed_by_host_connector_id
```

`host_connector_requests` is a new table matching the typed request/result envelope; legacy Command JSON is never copied into it. `host_connector_credential_rotations` provides the pending-hash/expiry/commit state defined in `DATA_AND_API_CONTRACTS.md`; the renamed credential row remains the single current hash.

HCON-002 ships a migration-only pre-cutover mode: `JulOS.Server --drain-legacy-agent-requests --deadline-seconds {60..3600}`. It runs against the old schema after every normal Server instance is stopped, binds the normal Agent-facing URL, exposes only legacy authentication, heartbeat, empty `commands/next` and completion for IDs already in `running`, and has no browser/admin/package/command-creation route. At startup it atomically marks queued rows `failed` with `agent.command_cancelled_for_upgrade`; exact completion retry for an already-terminal row remains idempotent. It exits zero only when no queued/running row exists, exits nonzero at deadline without changing a running row, and is stopped before schema migration. The migration independently rejects queued/running rows and an active drain process. This bounded migration tool is not a second product runtime or compatibility fallback.

Existing `succeeded`, `failed`, `expired` and `cancelled` rows move unchanged to read-only `legacy_agent_commands` for audit retention and have no runtime repository or endpoint. Tests inject queued, running and every terminal state and prove that no unknown side effect is reported as success.

IDs, credentials, capabilities, metrics, timestamps, revisions and audit history remain intact. PostgreSQL and SQLite upgrade fixtures prove this.

The existing `name` column renames to `display_name`. New non-null `protocol_version` is backfilled to `1`, the only accepted legacy Agent protocol, before its check constraint is added. No inferred version comes from the executable display version.

The existing machine-identity hash namespace remains the identity-v1 constant during migration so an enrolled machine does not change identity:

```text
MachineIdentityNamespaceV1 = UTF8("JulOS.Agent\0")
MachineIdentityV1          = lowercase-hex(SHA256(MachineIdentityNamespaceV1 || UTF8(trimmed machine-id source)))
```

The historical byte prefix is retained exactly; it is never localized or renamed to Host Connector. This is data compatibility, not a public Agent compatibility path. Changing it requires a new identity version and an explicit server-side association flow, never silent re-enrollment.

### 10.3 Identity file

One explicit migration command accepts `--legacy-identity-path` and `--host-connector-identity-path`; defaults come from the configured old/new environment variables and then the platform defaults (`/var/lib/julos-agent/identity.json` and `/var/lib/julos-host-connector/identity.json` on Linux). It accepts only an enrolled identity; a pending identity blocks migration and must complete or be deliberately discarded/re-enrolled before cutover.

The command validates regular-file/no-symlink/owner permissions, ID, CredentialV1 and MachineIdentityV1, writes the new file atomically with mode `0600`, re-reads it, and removes the old file only after verification. If both files exist and their protected identity fields are byte-equivalent, the command succeeds idempotently and may remove the verified old file; any difference fails `host_connector.identity_migration_conflict` without changing either. Windows uses the configured/ProgramData paths with an owner-only ACL. After successful migration only the new path is read. The old runtime route may exist for one announced transition release only as a `426` tombstone; it never executes legacy requests.

## 11. Container terminal boundary

A container terminal is a Docker-package action, not a Host Connector shell.

The Docker package request identifies:

```text
AppInstallationId
HostConnectorId
DockerEngineId
StableProjectIdentity
StableServiceIdentity
ResolvedContainerIdentity
ShellProfile                 auto | sh | bash
Columns
Rows
IdleTimeoutSeconds
MaximumDurationSeconds
IdempotencyKey
```

The Connector verifies that the current container belongs to the requested stable service and installation, opens only the requested profile and binds the exec stream to the resulting grant. It cannot execute a host command.

Permission: `docker.container.terminal`.

Audit records open, connect, disconnect, timeout, target and outcome. Keystrokes and terminal output are never written to audit or normal logs. Timeout or close must end the exec process and verify closure.

## 12. Hermes

Hermes is an example user workload, not a Core or Host Connector concept. It can be connected as an existing Compose application or installed from an app catalog. Its CLI is opened through the audited container-terminal flow. Telegram and any other Hermes interface remain owned by Hermes. A future native chat integration would be an optional JulOS extension using documented Hermes APIs, not Host Connector behavior.

## 15. Acceptance

- No current product UI, public API or new contract calls the component Agent.
- Existing enrolled identities, credentials, metrics and audit history survive both supported database upgrades.
- A revoked or legacy binary cannot execute a request after the cutover.
- Enrollment, heartbeat, diagnostics and Host Metrics retain their behavior under the new contract.
- Server and Runtime Manager expose neither a generic host shell nor a Docker proxy.
- Every capability rejects an unauthorized target locally even when Server sends a malformed request.
- A container terminal is scoped, permission-checked, time-bounded, audited and reliably terminated.
- Hermes works without special Core, Remote or Host Connector code.
