# JulOS 0.4.0-beta.12

Twelfth JulOS beta. It makes interactive Browser and Remote sessions connect reliably on the first attempt — even on a fresh host that still has to pull the runtime images — and tunes the SQLite deployment for JulOS's concurrent background writes. It changes only the Server; the official packages are byte-identical to `0.4.0-beta.8`.

## Fixed

- The first interactive Browser or Remote session on a fresh deployment no longer fails to connect. Provisioning ran under the caller's request deadline, so a slow first-image pull — or a reverse-proxy or client disconnect — cancelled it after the runtime container had already started. The started provider's connected-callback then could not match the torn-down session and failed with `404` ("the provider bridge failed to finalize the Guacamole launch"). The Server now runs the runtime launch and the state commit that records it independently of the caller's request lifetime, bounded by the Runtime Manager's own create timeout, so a started runtime is always matched by a consistent session. Pre-pulling the runtime images is now a speed optimization, not a correctness requirement.
- Reconciliation no longer removes the runtime of a session that is still starting. A `provisioning` or `connecting` session that had gone more than a minute without an activity write — a slow first-image pull — was selected by the coarse idle prefilter and had its runtime cleaned even though it was neither expired nor idle-due, stranding the starting provider. The reconciler now only cleans terminal or disconnecting sessions; a genuinely idle or expired session is still expired and cleaned as before.

## Changed

- SQLite deployments now open every connection in WAL journal mode with a five-second busy timeout and `synchronous=NORMAL`. This lets the single-file database carry JulOS's concurrent background writes (reconciler, per-session activity, audit, desktop-layout saves) without intermittent "database is locked" errors, and is faster than the previous defaults. PostgreSQL deployments are unchanged — the tuning is applied only in the SQLite path. WAL adds `julos.db-wal` and `julos.db-shm` sidecar files next to the database inside the existing data volume; these are normal and are checkpointed into the main file on a clean shutdown.
- The three official packages remain at `1.0.3`. This release changes only the Server; the package artifacts (Browser, Remote and Host Metrics) are byte-identical to `0.4.0-beta.8` and are not re-published.

## Deployment

The server image for this prerelease is:

`ghcr.io/juloc/julos-server:0.4.0-beta.12`

Existing data and keys remain compatible. Preserve `JULOS_PRIMARY_KEY`, `JULOS_RUNTIME_MANAGER_KEY` and `JULOS_REMOTE_PROVIDER_CALLBACK_KEY` when upgrading. The installed Browser, Remote and Host Metrics packages stay at `1.0.3`; no package update is required. On a SQLite deployment the database switches to WAL automatically on the first start after the upgrade.

Runtime images are unchanged and remain digest-pinned:

- Browser runtime: `ghcr.io/juloc/julos-browser-runtime@sha256:933a2a8b7bc260560d0c2459ca8aa102596ab282bb094eb690c5ecf767302a8a`
- Remote provider: `ghcr.io/juloc/julos-remote-provider@sha256:e9c9d61adb82e56370a5fdaa76344dab686b4afd90a2ce41fc82cfe3a510b643`

## Security boundary

Unchanged. No Docker socket in Server, immutable digest-pinned runtimes, Runtime Manager as the only Docker control plane, allowlisted runtime networks. No credential, target or trust policy is widened.

## Validation focus

- a first interactive session on a host without cached runtime images reaches `connected` and attaches its display
- a client or reverse-proxy disconnect during runtime provisioning does not strand the started provider
- reconciliation leaves a still-starting session's runtime in place and still expires genuinely idle sessions
- a SQLite deployment reports `journal_mode=wal` and `busy_timeout=5000`
- the official packages remain byte-identical at `1.0.3`
