# JulOS 0.4.0-beta.4

Fourth JulOS beta hotfix focused on the deployed Browser package and Remote VNC presentation path.

## Fixed

- The official Browser, Remote and Host Metrics packages are now `1.0.1`. Earlier beta server images rebuilt package workers with the JulOS server version while keeping package version `1.0.0`, so the same immutable package identity was published with different bytes and existing installations could remain on older signed artifacts.
- Official package workers are now built with their own manifest version, so an unchanged package no longer changes merely because the JulOS server version changes.
- Official package staging derives package versions and archive names from each package manifest, removing duplicated package-version literals from the catalog build.
- The release workflow refuses to publish different bytes under a package filename/version that already exists in a previous release.
- The Remote provider accepts the password-only VNC credential produced by isolated interactive Browser sessions while keeping the existing structured JSON credential contract for normal saved Remote connections.
- Desktop API errors now retain caller-safe `{ code, detail }` responses even when an endpoint returns ordinary `application/json` rather than Problem Details.
- Browser session startup surfaces the actual caller-safe capability failure message instead of reducing every create failure to `Browser session could not be started.`

## Deployment

The server image for this prerelease is:

`ghcr.io/juloc/julos-server:0.4.0-beta.4`

Existing Beta3 data and keys remain compatible. Preserve `JULOS_PRIMARY_KEY`, `JULOS_RUNTIME_MANAGER_KEY`, and `JULOS_REMOTE_PROVIDER_CALLBACK_KEY` when upgrading.

After redeploying the Beta4 server, open the JulOS package catalog and update the already-installed official packages from `1.0.0` to `1.0.1`. Package updates remain operator-controlled; JulOS does not silently replace installed packages during server startup. Existing package configuration and enabled state are preserved by the normal update path.

The Browser Runtime image itself is unchanged and remains pinned to:

`ghcr.io/juloc/julos-browser-runtime@sha256:933a2a8b7bc260560d0c2459ca8aa102596ab282bb094eb690c5ecf767302a8a`

The Remote Provider runtime is rebuilt for Beta4 because its VNC credential adapter changed. Deploy the Beta4-published Remote Provider digest together with the Beta4 server image.

## Security boundary

The JulOS Server still has no Docker socket. Runtime images remain immutable digest-pinned, Runtime Manager remains the only Docker control-plane component, runtime networks remain allowlisted, and no target or credential policy is widened by this hotfix.

## Validation focus

- existing official `1.0.0` installations can update to `1.0.1` while preserving configuration and enabled state
- unchanged package builds remain stable across future JulOS server releases
- Browser create failures expose caller-safe server detail
- interactive Browser VNC credentials are accepted by the Remote Provider
- normal JSON API failures retain stable code/detail metadata
- Browser and Remote runtimes remain isolated on the configured Runtime Manager network
