# JulOS 0.4.0-beta.16

Released 2026-08-23.

## Summary

Sixteenth JulOS beta and the first published prerelease since `0.4.0-beta.15` was prepared but never released, so this build also carries the beta.15 Remote-provider tunnel-authentication correction. It adds local web-application rendering (WEB-001), a same-browser multi-display desktop workspace, and closes a web-application proxy authorization gap. It also defaults the core store to SQLite for single-host deployments.

## Upgrade

| Question | Answer |
|---|---|
| Minimum previous version | `0.4.0-beta.14` |
| Database migration required | no |
| Migration reversible | n/a |
| Downtime expected | brief restart |
| Safe mode required | no |

The core store now defaults to SQLite when no database provider or connection string is configured (decision `D033`). Existing PostgreSQL deployments are unaffected as long as `ConnectionStrings__CoreDatabase` / `Database__Provider` remain set.

After upgrading, open the JulOS package catalog and update the installed Browser, Remote and Host Metrics packages to `1.0.4`; configuration and enabled state are preserved. The `1.0.4` artifacts are a reproducible rebuild of the same functionality as `1.0.3`, republished because `JulOS.Contracts` changed since the `1.0.3` build.

## Breaking changes

- **Web-application access now requires a permission.** Accounts that could previously open local web applications only because they were authenticated can no longer do so unless they hold the new `core.webapp.use` permission. The administrator role receives it automatically; grant it to other roles explicitly. See Security.

## Added

- **Local web-application rendering (WEB-001, D035):** internal web apps render in the user's own browser through a transparent per-host reverse proxy, including a dynamic "type a URL" address-bar browser window over a default-deny hostname/CIDR allowlist.
- **Multi-display desktop workspace:** two or more authenticated JulOS browser windows in the same profile and origin form one ordered workspace, with window hand-off across adjacent display edges and recovery of a disappearing display's windows. Browsers without `BroadcastChannel` continue as a normal single-display session.
- **Interactive-session orchestration test coverage** for the Browser package (issue #61).

## Changed

- Core store defaults to SQLite for single-host installs; PostgreSQL remains supported and opt-in (`D033`).
- Remote Provider exchanges encrypted Guacamole JSON-auth `data` through `/api/tokens`, supplies the per-session JSON connection selectors, and reports `connected` only after the web application, authentication exchange and nginx listener are ready (carried from the unreleased beta.15).
- Every Node test stage is now bounded by a per-test timeout so a hung test fails fast instead of consuming the whole CI job.
- Documentation reconciled with shipped reality (DESK-015/016 status, WORK_BREAKDOWN status source, API-001 vs `D033`, `D005` ↔ `D035`, and the signing-key custody vs `REL-PKG-001` distinction).
- The three official packages advance to `1.0.4`: the same functionality as `1.0.3`, rebuilt because `JulOS.Contracts` changed since the `1.0.3` build (WEB-001 web-application contracts and the new `core.webapp.use` permission), so the prior `1.0.3` bytes can no longer be reproduced.

## Fixed

- Browser package interactive-session cleanup clock injection, problem deduplication and runtime startup-grace handling.
- The multi-display workspace no longer keeps a Node test host alive (its heartbeat and channel are unref'd where the runtime supports it).
- The interactive-session orchestration test project now compiles (unblocking its coverage).

## Security

- **Web-application proxy authorization.** The local web-application reverse proxy and the `/api/v1/webapps` discovery endpoints previously required only an authenticated session, so any authenticated account could reach every configured static target and, in dynamic mode, every CIDR-allowlisted internal origin — including internal administrative UIs that role-based access would otherwise restrict. They now require the new `core.webapp.use` permission (held by the administrator role by default); an authenticated account without it receives `403`. Default single-administrator installations were the common case; multi-user installations with non-administrator accounts were exposed. No credential disclosure was involved.
- Dynamic web-application proxy connections are pinned to the validated resolved IP set on both the HTTP and WebSocket paths (DNS-rebinding / SSRF hardening).

## Known limitations

- Deployed rendered-display acceptance for RDP, VNC, SSH and Browser against the pinned provider image remains open (issues #37 / #41 / #43 / #45).
- Remaining WEB-001 work: body/reference rewriting, the runtime shim, Agent-tunnel reachability, server-side credential injection and the `auto` streamed fallback.
- Appearance personalization: a user-selectable accent, appearance presets and wallpaper/density controls are deferred (see DESK-016).
