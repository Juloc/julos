# JulOS 0.4.0-beta.10

Tenth JulOS beta. It completes the Browser display fix from `0.4.0-beta.9`: an interactive session's display descriptor is issued on `read` once the session is connected and is always bound to the session's current revision, so the Browser reliably attaches its remote canvas. It changes only the Server; the official packages are byte-identical to `0.4.0-beta.8`.

## Fixed

- The Browser display descriptor is always current. `interactive.session` `read` (and the idempotent create-recovery path) issue a fresh same-origin display descriptor for the owning caller once the session is connected, and now re-issue on every connected read instead of returning a stored descriptor. The descriptor is revision-bound and display authorization refuses it unless its revision matches the session's current revision; a stored descriptor can go revision-stale after any non-resume revision bump (recorded activity, for example) and would then fail to authorize. Re-issuing rebinds it to the current revision. In the normal flow the frontend attaches on the first connected read and stops polling, so this still issues once; a resume refusal surfaces the connected session without a display so the caller reads again rather than receiving a descriptor that cannot authorize. (`0.4.0-beta.9` introduced the on-read issuance; this release makes it revision-robust.)

## Carried from 0.4.0-beta.9

- A Browser (`interactive.session`) session that reaches `connected` now receives a display descriptor through `read`; previously it stayed `null` and the Guacamole canvas never attached.
- The alpha PostgreSQL compose starts the Server: its `migrate` service now runs the full `dotnet /application/JulOS.Server.dll --migrate-database` invocation instead of passing `--migrate-database` as the container command.
- The dev remote compose pins the shared runtime network to the literal name `julos-remote` so Runtime Manager's bare `--network julos-remote` attach resolves.

## Changed

- The three official packages remain at `1.0.3`. This release changes only the Server; the package artifacts (Browser, Remote and Host Metrics) are byte-identical to `0.4.0-beta.8` and are not re-published.

## Deployment

The server image for this prerelease is:

`ghcr.io/juloc/julos-server:0.4.0-beta.10`

Existing data and keys remain compatible. Preserve `JULOS_PRIMARY_KEY`, `JULOS_RUNTIME_MANAGER_KEY` and `JULOS_REMOTE_PROVIDER_CALLBACK_KEY` when upgrading. The installed Browser, Remote and Host Metrics packages stay at `1.0.3`; no package update is required.

Runtime images are unchanged and remain digest-pinned:

- Browser runtime: `ghcr.io/juloc/julos-browser-runtime@sha256:933a2a8b7bc260560d0c2459ca8aa102596ab282bb094eb690c5ecf767302a8a`
- Remote provider: `ghcr.io/juloc/julos-remote-provider@sha256:e9c9d61adb82e56370a5fdaa76344dab686b4afd90a2ce41fc82cfe3a510b643`

## Security boundary

Unchanged. Display issuance reuses the existing Remote resume: the descriptor is scoped to the owning user and package, revision-bound, same-origin and short-lived, and is re-authorized at display-connect time. No Docker socket in Server, immutable digest-pinned runtimes, Runtime Manager as the only Docker control plane, allowlisted runtime networks. No credential, target or trust policy is widened.

## Validation focus

- a connected interactive session's `read` returns a same-origin display descriptor bound to the session's current revision, and a read after a revision bump returns a freshly rebound descriptor
- the display WebSocket authorizes the issued descriptor and refuses stale or expired ones
- the alpha PostgreSQL stack migrates and starts, and the server reaches a healthy state
- the official packages remain byte-identical at `1.0.3`
