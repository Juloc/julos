# JulOS 0.4.0-beta.3

Third JulOS beta hotfix focused on reliable first-start provisioning for interactive Browser sessions.

## Fixed

- Browser session creation no longer inherits the generic 10-second capability deadline.
- `interactive.session/create` now has a bounded six-minute provisioning window so a first Browser launch can pull and create the pinned Chromium runtime image before the capability expires.
- The Runtime Manager client keeps the normal 30-second timeout for ordinary control-plane calls, while runtime creation receives a bounded five-minute timeout for image provisioning.
- This fixes the Beta2 failure mode where Runtime Manager logged HTTP 499 during `POST /v1/runtimes/`, Docker still left a `julos-interactive-*` container in `Created`, and JulOS never reached the subsequent start request.

## Unchanged security boundary

The JulOS Server still does not receive the Docker socket. Only Runtime Manager owns Docker access, Browser runtime images remain immutable digest-pinned package configuration, and package/runtime network policy remains unchanged.

## Deployment

The server image for this prerelease is:

`ghcr.io/juloc/julos-server:0.4.0-beta.3`

Existing Beta2 data and keys remain compatible. Preserve `JULOS_PRIMARY_KEY`, `JULOS_RUNTIME_MANAGER_KEY`, and `JULOS_REMOTE_PROVIDER_CALLBACK_KEY` when upgrading.

The Browser Runtime itself is unchanged and remains pinned to:

`ghcr.io/juloc/julos-browser-runtime@sha256:933a2a8b7bc260560d0c2459ca8aa102596ab282bb094eb690c5ecf767302a8a`

## Validation focus

- first Browser launch when the runtime image is not yet local
- subsequent Browser launches with the runtime image already cached
- verify Runtime Manager reaches `/v1/runtimes/{runtimeId}/start` after create
- verify the dynamic `julos-interactive-*` container becomes running and healthy without manual `docker start`
