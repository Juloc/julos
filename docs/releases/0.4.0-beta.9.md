# JulOS 0.4.0-beta.9

Ninth JulOS beta. It makes the Browser app actually present its display: an interactive session now receives a display descriptor as soon as it is connected, so the Browser (and any `interactive.session` package) attaches its remote canvas. It also carries two deployment fixes found during end-to-end validation. It changes only the Server; the official packages are byte-identical to `0.4.0-beta.8`.

## Fixed

- The Browser display now attaches. `interactive.session` `read` (and the idempotent create-recovery path) issue and persist a fresh same-origin display descriptor for the owning caller once the session is connected. Previously the caller-safe descriptor was minted only by a Remote `resume`, which the `interactive.session` capability never invoked, so a connected Browser session returned `display: null` indefinitely and the Guacamole canvas never attached. The descriptor's identity, revision binding and 60-second expiry are unchanged (it reuses the existing Remote resume), a stored unexpired descriptor is returned as is so repeated reads stay idempotent, and a resume refusal falls back to the plain snapshot so a read never fails on presentation issuance alone.
- The alpha PostgreSQL compose starts the Server. Its `migrate` service passed `--migrate-database` as the container command, but the image entrypoint runs `exec gosu <uid> "$@"`, so it was treated as the executable and the migrate service failed with "executable file not found" — the Server never started. It now runs the full `dotnet /application/JulOS.Server.dll --migrate-database` invocation.
- The dev remote compose runtime network resolves. It declared the shared runtime network without an explicit name, so Compose created it project-prefixed (`<project>_julos-remote`) while Runtime Manager attaches with a bare `docker run --network julos-remote`; the network is now pinned to the literal name `julos-remote` so the Server, Runtime Manager and launched runtimes all resolve the same on-host network.

## Changed

- The three official packages remain at `1.0.3`. This release changes only the Server; the package artifacts (Browser, Remote and Host Metrics) are byte-identical to `0.4.0-beta.8` and are not re-published.

## Deployment

The server image for this prerelease is:

`ghcr.io/juloc/julos-server:0.4.0-beta.9`

Existing data and keys remain compatible. Preserve `JULOS_PRIMARY_KEY`, `JULOS_RUNTIME_MANAGER_KEY` and `JULOS_REMOTE_PROVIDER_CALLBACK_KEY` when upgrading. The installed Browser, Remote and Host Metrics packages stay at `1.0.3`; no package update is required.

Runtime images are unchanged and remain digest-pinned:

- Browser runtime: `ghcr.io/juloc/julos-browser-runtime@sha256:933a2a8b7bc260560d0c2459ca8aa102596ab282bb094eb690c5ecf767302a8a`
- Remote provider: `ghcr.io/juloc/julos-remote-provider@sha256:e9c9d61adb82e56370a5fdaa76344dab686b4afd90a2ce41fc82cfe3a510b643`

## Security boundary

Unchanged. The new display issuance reuses the existing Remote resume: the descriptor is scoped to the owning user and package, revision-bound, same-origin and short-lived, and is re-authorized at display-connect time. No Docker socket in Server, immutable digest-pinned runtimes, Runtime Manager as the only Docker control plane, allowlisted runtime networks. No credential, target or trust policy is widened.

## Validation focus

- a connected interactive session's `read` returns a same-origin display descriptor, and re-reads are idempotent
- the display WebSocket authorizes the issued descriptor and refuses stale or expired ones
- the alpha PostgreSQL stack migrates and starts, and the server reaches a healthy state
- the official packages remain byte-identical at `1.0.3`
