# JulOS 0.4.0-beta.13

Thirteenth JulOS beta. It stops the desktop layout save from crashing with a unique-constraint error when a window's stacking order changes — a crash that left interactive Browser and Remote windows stuck at "connecting" even after the session had connected. It changes only the Server; the official packages are byte-identical to `0.4.0-beta.8`.

## Fixed

- Saving a desktop layout no longer fails with `UNIQUE constraint failed: desktop_windows.desktop_layout_id, z_index` (which surfaced as an unhandled 500). Whenever a window's stacking order changed — bringing a window to the front, opening a new window, or closing one in the middle — the Server re-wrote the windows in a single change batch that could insert or update a `z_index` before deleting the row that still held it, tripping the unique index. Because the desktop persists the layout as soon as a window opens, this 500 left Browser and Remote (RDP/SSH/VNC) windows stuck at "creating session…" / "connecting…" even though the underlying session had already connected and issued its display. The Server now deletes the previous windows and widgets and flushes that delete before inserting the new set, inside one transaction, so the stacking order can change freely.

## Carried from the 0.4.0-beta.12 line

- Interactive Browser and Remote sessions connect reliably on the first attempt: runtime provisioning is no longer cancelled by the caller's request deadline, and reconciliation no longer removes the runtime of a still-starting session (`0.4.0-beta.12`).
- SQLite deployments open every connection with WAL journal mode, a five-second busy timeout and `synchronous=NORMAL` (`0.4.0-beta.12`).

## Changed

- The three official packages remain at `1.0.3`. This release changes only the Server; the package artifacts (Browser, Remote and Host Metrics) are byte-identical to `0.4.0-beta.8` and are not re-published.

## Deployment

The server image for this prerelease is:

`ghcr.io/juloc/julos-server:0.4.0-beta.13`

Existing data and keys remain compatible. Preserve `JULOS_PRIMARY_KEY`, `JULOS_RUNTIME_MANAGER_KEY` and `JULOS_REMOTE_PROVIDER_CALLBACK_KEY` when upgrading. The installed Browser, Remote and Host Metrics packages stay at `1.0.3`; no package update is required.

Runtime images are unchanged and remain digest-pinned:

- Browser runtime: `ghcr.io/juloc/julos-browser-runtime@sha256:933a2a8b7bc260560d0c2459ca8aa102596ab282bb094eb690c5ecf767302a8a`
- Remote provider: `ghcr.io/juloc/julos-remote-provider@sha256:e9c9d61adb82e56370a5fdaa76344dab686b4afd90a2ce41fc82cfe3a510b643`

## Security boundary

Unchanged. No Docker socket in Server, immutable digest-pinned runtimes, Runtime Manager as the only Docker control plane, allowlisted runtime networks. No credential, target or trust policy is widened.

## Validation focus

- reordering, opening and closing desktop windows persists the layout without a unique-constraint error
- an interactive Browser or Remote window reaches its display instead of remaining at "connecting"
- a SQLite deployment reorders windows without a "database is locked" or unique-constraint failure
- the official packages remain byte-identical at `1.0.3`
